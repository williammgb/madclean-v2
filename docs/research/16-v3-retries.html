v3: did the retry changes cut the extra rounds?

Ticket #16 · four live runs on Gemini 2.5 Pro, 2026-10-25 · compared with the runs of 2026-10-02 and 2026-10-04

1. The question

Measure whether the changes worked: one paid live run each of beers, hospital, movies and rayyan on the finished v3, compared with the 2–4 October runs on extra rounds, failed columns, tokens, time and correction F1.

2. The answer

Yes — the target is met. Hospital, movies and rayyan together took 15 extra rounds instead of about 42 (9 + 9 + ~24), no column failed (rayyan had 2 before), every run used fewer tokens (14–32% fewer), and correction F1 stayed within 0.02 of before or got better: hospital −0.004, beers −0.003, movies +0.032, rayyan +0.185.

Two things did not get better: movies and hospital took longer to run even with fewer tokens, and rayyan's author_list column still uses 62% of rayyan's tokens and ends without the Validator's approval. Hospital's low score has a separate cause: two columns the Recommender calls clean. Each of these is a follow-up ticket below.

3. Before and after

"Extra rounds" means rounds after the first, per column, added up over the dataset. Before, each round was counted from the log's "Validation Agent detected unintended changes" lines. After, it comes from attempts − 1 in each column's agent_stats. Since #20, a Validator objection can be fixed by repairing the cells it names and asking it once more, without a whole new round, so "Validator objections" is shown as well. Before, every objection started a new round, so the before count of objections equals the before count of rounds.

Cost of the four runs at $1.25 per million input tokens and $10 per million output tokens: beers $0.89, hospital $1.44, movies $1.92, rayyan $3.59 — $7.83 in total, within the $8 that was approved. Rayyan wrote more output than before (322,519 against 252,035 tokens), almost all of it for author_list, so it cost more than its $3.10 estimate.

What changed, in one paragraph

The extra rounds dropped mainly because objections are now fixed in place — the Validator objected about as often as before (movies 15 times against 9, rayyan 15 against ~24, hospital 6 against 9), but most objections now cost one repair and one more Validator call instead of a whole round: in hospital, Sample, Stateavg, ProviderNumber, Address1 and MeasureName each needed one to three new rounds before and none now, and rayyan's columns no longer run all the way to the old limit of 6 rounds (the limit is 4 now, and a column stops after two Coder failures in a row or the same objection twice). The round limit together with the 3-minute call limit is also why rayyan finished in 33 minutes instead of 44 hours. Fewer rounds and shorter history in the Validator's prompt (#22) meant fewer tokens on every dataset. The cleaning did not get worse: movies and rayyan scored clearly higher, and beers and hospital stayed within 0.005. What is left: movies still took 8 extra rounds, and 3 of them (Language, Release Date, Country) — plus beers' city — were rounds where the Validator rejected the first rewrite and the Recommender then said the column was clean after all. Each of those is a full round spent only to undo a rewrite. Hospital took one column (Score) to 3 extra rounds where it took 1 before.

5. Still unknown

  • Why movies and hospital got slower (440 s against 249 s, 373 s against 318 s) with fewer tokens. It may be the model's response time that day, a call that hit the 3-minute limit and was retried, or the extra "ask once more" calls. The run record keeps no time per call, so this cannot be told apart; a per-call duration in agent_stats would settle it.
  • How much of the change is luck. Each dataset ran once, before and after. The rounds dropped far more than one run's spread is likely to explain, but the F1 changes of a few thousandths on beers and hospital are within noise.
  • Beers before: its rounds and failed columns of 2026-10-04 are not on disk.

6. Suggested follow-up tickets

Rayyan author_list: clean the authors one at a time, and stop the long code

author_list took 3 extra rounds and 7 objections, used 380,695 of rayyan's 612,174 tokens, and ended without approval with 84 errors missed and 35 correct cells broken. Its code grew into a hard-coded list of name fixes. Split each cell into its authors, let the Recommender give a value table for the distinct broken names, and join them back, so the Validator judges names rather than whole lists. Effort: normal.

Rayyan article_pagination and journal_abbreviation

article_pagination now passes but still misses 47 of 102 errors, and journal_abbreviation, which has no errors, had 22 cells changed. Look at the missed page ranges and the changed abbreviations and add the pattern to the Recommender's prompt or a guard for columns the profile finds consistent. Effort: small.

Hospital recall: tell the Recommender the dataset's rules

1,940 of hospital's 2,088 missed cells are Address2 "empty" (should be blank) and Sample "33 patients" (should be "33"). Either add hints for those columns to recommender_column_hints for the benchmark, or teach the Recommender that a placeholder word such as "empty" means a blank cell and that a number column with one constant unit should lose the unit. Effort: small.

FD repair: use the other rows instead of blanking

Hospital's 34 PhoneNumber typos were turned into blank cells, though the same provider's other rows hold the right number; most dependency checks said "No FD errors detected after cleaning". Let the dependency stage fill a broken cell with the value its group agrees on (majority within ProviderNumber → PhoneNumber and similar), before falling back to blank. Effort: normal.

Skip the round that only undoes a rewrite

4 of the 10 extra rounds in beers and movies (city, Language, Release Date, Country) were: the Validator rejects the first rewrite, then the Recommender says the column was clean all along. When the Validator's objection is that the rewrite changed correct values and asks for none to be kept, end the column as clean without a new Recommender round. Effort: small.

Record how long each model call takes

Movies ran 77% longer with 28% fewer tokens, and nothing on disk says why. Add each call's duration and whether it hit the 3-minute limit to agent_stats, so the next live run shows where the time went. Effort: small.

\chapter{Evaluation}
In this chapter, we evaluate the effectiveness of the proposed framework.
The evaluation focuses on analysing how well the framework detects errors, how accurately it repairs these errors and how its performance compares to existing state-of-the-art data cleaning approaches.
In addition, we also analyze the impact of the individual framework components.
\section{Experimental Setup}
To evaluate the performance of the proposed framework, we designed an experimental setup in which its results are compared against a set of baseline methods discussed in the literature review. 
These baselines were selected because they either use LLMs for data cleaning or demonstrate state-of-the-art performance on benchmark datasets.
Several LLM-based cleaning methods discussed before could not be included in the evaluation because their source code is not publicly available (e.g., LLMClean, IterClean).
Other methods focus exclusively on a specific error type, such as dependency violations, schema-level inconsistencies or DMVs (e.g., FAHES, SynODC). 
Since the proposed framework is designed for general-purpose data cleaning, these methods were excluded to ensure a meaningful comparison.

The evaluation is divided into two main phases:
\begin{enumerate}
  \item \textbf{Error Detection:} measuring whether the system correctly identifies erroneous cells in the dataset.
  \item \textbf{Error Correction:} measuring whether the system provides the correct repaired value for the detected errors.
\end{enumerate}

In addition to accuracy metrics, we compare the runtime performance of all evaluated methods. 
For the proposed framework, we further conduct a more detailed analysis that includes an analysis of LLM token usage per dataset and an ablation study to evaluate the contribution of individual framework components to the overall performance.
\newline\newline
Unless stated otherwise, all experiments use the \texttt{gemini-2.5-pro} model with default parameters (e.g., temperature = 1). 
Since LLMs are non-deterministic and framework performance may vary between runs, results are reported as the mean of four independent executions to improve robustness. 
All experiments were conducted on a laptop equipped with an Intel(R) Core(TM) i7-8750H CPU (6 cores, 12 logical processors, base frequency 2.20 GHz), 16 GB of RAM, running Microsoft Windows 11 (Version 24H2).

\subsection{Datasets}
The evaluation is conducted using four benchmark datasets that are commonly used in prior data cleaning research. 
All datasets have a corresponding ground truth version, which is used as a reference for computing the evaluation metrics. 
Initially, these versions still contained inconsistencies and were manually curated to ensure a reliable evaluation. 
Examples are standardizing representations of missing values (e.g., replacing placeholders with NaN), converting formatting inconsistencies (e.g., converting '10\%' to 10) and fixing minor typos.
To evaluate the robustness of the cleaning methods, additional outliers were injected into the Movies and Beers datasets. The Rayyan dataset already contains natural outliers and was therefore not modified.
An overview of the datasets is provided below. Dataset size and error rates are reported separately in table \ref{tab:datasets}.
\newline\newline
\textbf{Hospital} \cite{HOLOCLEAN} - A real-world, structured and redundant dataset describing hospitals and their attributes. The data consists primarily of short strings and numeric fields representing identifiers (e.g., zipcodes, phonenumber, ids). Errors include typos caused by character replacement (e.g., replacing characters with 'x'), formatting inconsistencies (e.g., values stored with non-numeric characters instead of pure numerics), DMVs such as 'empty' and dependency violations.
\newline
\textbf{Beers} \cite{RAHA}- A real-world, structured and redundant dataset containing information about beers and their properties, such as alcohol by volume and brewery details. The dataset includes numeric columns, short strings and identifiers. Error types include missing values, formatting inconsistencies (e.g., '0.045\%' vs 0.045, '12.0 oz' vs '12.0 ounce'), dependency violations, schema violations where data from multiple columns is merged into a single column, and some outliers and typos.
\newline
\textbf{Movies} \cite{MDR} - A real-world, structured dataset containing information about movies, including cast, ratings, duration and textual descriptions. The dataset includes a diverse range of data types, such as dates, numeric values, identifiers, multi-value columns and free-text fields. Error types include missing values, DMVs (e.g., 'No description'), outliers and formatting inconsistencies, such as pattern violations, incorrect data types and duplicated values.
\newline
\textbf{Rayyan} \cite{RAYYAN} - A real-world dataset with a high degree of unstructured columns with heterogeneous representations and limited redundancy, describing academic journals and their metadata, including publication dates, venues and authors. The dataset contains dates, numeric values, identifiers and text fields with inconsistent casing, diverse textual styles and substantial noise. Error types include typos, missing values, DMVs (e.g., -1, {NULL}), outliers and formatting inconsistencies

\subsection{Baselines}
To compare the proposed framework against existing methods, we include several data cleaning systems. 
All baselines support general-purpose data cleaning, except for SAGED, which is limited to error detection. 
For each method, the default parameters provided in the corresponding GitHub repositories were used to ensure fair comparisons. 
More detailed descriptions of these methods can be found in the related work section.
\newline\newline
\textbf{Raha}+\textbf{Baran} \cite{RAHA,BARAN} - An end-to-end data cleaning pipeline in which Raha performs error detection and Baran handles error correction based on the data from Raha. 
The error detection results therefore relate to Raha, while the error correction results depend on both Raha and Baran. 
Both components rely on machine learning models.
\newline
\textbf{HoloClean} \cite{HOLOCLEAN} - A probabilistic data cleaning framework that detects and repairs errors by using integrity constraints and redundancy in the data. 
It is particularly effective on datasets where errors can be accurately modeled using constraints.
\newline
\textbf{RetClean} \cite{RETCLEAN} - An LLM-based data cleaning framework that augments the cleaning process with contextual information from a data lake. 
In this evaluation, no external data lake is provided, so the model must rely on its own general knowledge and the context of other columns in the row for cleaning the values.
For RetClean, we implemented an asynchronous wrapper and used the model \texttt{gemini-2.5.flash-lite}, as the estimated runtime with other models was impractically large.
\newline
\textbf{Cocoon} \cite{COCOON} - An LLM-based data cleaning approach that applies statistical analysis to summarize dataset characteristics and then uses these summaries to guide the LLM during the cleaning process.
\newline
\textbf{SAGED} \cite{SAGED} - A machine learning-based error detection system. Since SAGED requires labeled data for training, its base models were trained on the Flights \cite{HOLOCLEAN} dataset.

\subsection{Evaluation measures}
To evaluate the effectiveness of the data cleaning systems, we follow the standard evaluation protocol used in prior data cleaning research. 
The evaluation is performed at the cell level, where each cell in the dataset is treated as an individual prediction. 
We distinguish between error detection and error correction, while using a single, consistent definition of precision, recall and F1 score for both tasks.
\newline\newline
The term mask is commonly used in data cleaning literature to denote a boolean matrix that indicates specific properties of cells (e.g., whether a cell is erroneous, modified or correctly repaired). We therefore use this terminology throughout the evaluation.
\newline\newline
Let $D_d$ denote the dirty dataset and $D_{gt}$ the corresponding ground truth dataset. 
By comparing these two datasets, we construct the \emph{error mask}, which indicates the cells that are erroneous in the dirty dataset:
\[
E_{ij} =
\begin{cases}
1 & \text{if } D_d[i,j] \neq D_{gt}[i,j], \\
0 & \text{otherwise}.
\end{cases}
\]

Next, the data cleaning system is applied to $D_d$, producing the cleaned dataset $D_c$. 
From this, we define the \emph{change mask}, which captures all cells that were modified by the cleaning system:
\[
C_{ij} =
\begin{cases}
1 & \text{if } D_d[i,j] \neq D_c[i,j], \\
0 & \text{otherwise}.
\end{cases}
\]

Finally, we define a \emph{correction mask} that indicates whether the cleaned value matches the ground truth value:
\[
Q_{ij} =
\begin{cases}
1 & \text{if } D_c[i,j] = D_{gt}[i,j], \\
0 & \text{otherwise}.
\end{cases}
\]

This mask is used exclusively for evaluating correction quality.

\subsubsection{Error Detection}
For error detection, a cell is considered predicted as error if the cleaning system modifies it ($C_{ij}=1$). 
A cell is actually erroneous if it differs from the ground truth ($E_{ij}=1$).
Based on these definitions, we define:
\[
\textbf{True Positives (TP)} = \{(i,j) \mid E_{ij} = 1 \land C_{ij} = 1\}
\]
\indent Erroneous cells that are correctly detected (i.e., changed by the system).

\[
\textbf{False Positives (FP)} = \{(i,j) \mid E_{ij} = 0 \land C_{ij} = 1\}
\]
\indent Clean cells that are incorrectly modified by the system.

\[
\textbf{False Negatives (FN)} = \{(i,j) \mid E_{ij} = 1 \land C_{ij} = 0\}
\]
\indent Erroneous cells that are not detected by the system.

True Negatives (clean cells that remain unchanged) do not provide useful information in this context and are therefore excluded.

Using these sets, precision, recall, and F1 score are computed as:
\[
\textbf{Precision} = \frac{|\text{TP}|}{|\text{TP}| + |\text{FP}|}
\]

\[
\textbf{Recall} = \frac{|\text{TP}|}{|\text{TP}| + |\text{FN}|}
\]

\[
\textbf{F1 score} = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}
\]

Precision measures how many of the detected cells are truly erroneous, while recall measures how many of the actual erroneous cells are detected by the system.

\subsubsection{Error Correction}
For error correction, we evaluate whether the system not only detects an error but also repairs it correctly. A cell is considered correctly repaired if it is erroneous, modified by the system, and equal to the ground truth ($Q_{ij}=1$) after cleaning.
We therefore redefine the cases as:
\[
\textbf{True Positives (TP)} = \{(i,j) \mid E_{ij} = 1 \land C_{ij} = 1 \land Q_{ij} = 1\}
\]
\indent Erroneous cells that are changed and repaired correctly.

\[
\textbf{False Positives (FP)} = \{(i,j) \mid C_{ij} = 1 \land Q_{ij} = 0\}
\]
\indent Cells that are modified but not repaired correctly, including both incorrectly changed clean cells and incorrectly repaired erroneous cells.

\[
\textbf{False Negatives (FN)} = \{(i,j) \mid E_{ij} = 1 \land Q_{ij} = 0\}
\]
\indent Erroneous cells that are not repaired correctly, either because they were not changed or because they were changed to an incorrect value.

We use the same formulas for precision, recall, and F1-score as described above to maintain consistency. 
In this context, precision reflects how many of the modified cells are repaired correctly, while recall reflects how many of the true errors in the dataset are repaired correctly.

\section{Results}
In this section, we present the experimental results of the proposed framework. 
We first summarize the error detection and error correction performance based on the results shown in the tables. 
Next, we discuss the observed cleaning behavior across the individual datasets and compare the proposed framework with the baseline methods. 
Finally, we analyze runtime performance and provide a more in-depth evaluation of the framework.

\subsection{Error detection results}
The error detection results in table \ref{tab:detection_results} show that the proposed framework consistently outperforms the baseline methods across most datasets. 
It achieves high precision and recall, resulting in near-perfect F1 scores for all datasets except Rayyan. 
On the Rayyan dataset, Raha+Baran slightly outperforms the proposed framework in terms of F1 score.
The framework demonstrates high recall across all datasets, showing that it effectively identifies erroneous cells. 
At the same time, it maintains high precision, meaning that only few clean cells are incorrectly modified. 
This is an important property for data cleaning systems, as unnecessary changes to clean values can negatively affect overall data quality.
Performance is generally higher on highly structured datasets, such as Hospital, Beers. 
In contrast, all evaluated methods perform substantially worse on the Rayyan dataset. 
This dataset contains unstructured columns with ambiguous styles and limited redundancy, making error detection more challenging.
\newline\newline
Among the baseline methods, HoloClean exhibits the weakest detection performance across datasets, largely due to its preprocessing step that converts all values to lowercase, which introduces many false positives. 
In addition, HoloClean failed to complete the cleaning process for the Movies dataset due to excessive memory requirements (it attempted to allocate 50 GB of memory). 
RetClean also shows low detection performance and did not finish execution on the Movies dataset within the 15-hour timeout. 
Analysis of its cleaned outputs indicates a high number of false positives, mainly caused by unstable LLM responses and inconsistent parsing. 
SAGED achieves moderate detection performance but suffers from low precision, as it tends to overgeneralize errors and frequently flags entire columns as erroneous even when only a subset of cells contains errors. 
Cocoon performs reasonably well on the Hospital and Beers datasets but is less consistent on the Movies and Rayyan datasets, where detection accuracy drops notably. 
Finally, Raha+Baran shows strong and consistent detection performance across the datasets, achieving F1 scores above 0.90 on all datasets except Rayyan. 
Its performance is comparable to that of the proposed framework, highlighting that it remains a strong baseline for error detection tasks.

\subsection{Error correction results}
The error correction results shown in table \ref{tab:correction_results} further highlight the effectiveness of the proposed framework. 
It outperforms all baseline methods or achieves equivalent performance across all datasets, while consistently maintaining high precision and recall. 
For three of the four benchmark datasets, the framework achieves F1 scores above 0.96. 
High precision indicates that most detected errors are repaired correctly, while high recall shows that the majority of all existing errors in the dataset are successfully corrected.
\newline\newline
In contrast, several baseline methods struggle with reliable error correction. 
RetClean exhibits low precision, indicating that many detected errors are repaired incorrectly. 
HoloClean achieves near-zero correction performance on most datasets, with the exception of Hospital. 
This can be explained by the high level of redundancy and the strong constraints in the dataset, which HoloClean can effectively utilize to repair values. 
Cocoon shows high recall on three datasets but has lower precision and exhibits inconsistent performance across datasets. 
Raha+Baran achieves strong correction results, with F1 scores above 0.91 across all datasets, confirming its effectiveness as an end-to-end data cleaning system. 
Since SAGED is designed only for error detection, it is excluded from this evaluation.

\subsubsection{Dataset-level analysis}
We discuss the cleaning results of the proposed framework for each dataset, highlighting which errors are effectively corrected, which remain, and the reasons behind these outcomes. 
\newline\newline
\textbf{Hospital} - The proposed framework achieves strong performance on the Hospital dataset, both for error detection and correction. 
It successfully identifies and repairs a wide range of errors across identifiers, categorical fields and numeric columns. 
This success is largely due to the structured nature of the dataset, the presence of redundant data and the ability of the framework to leverage functional dependencies and column-level context.
The framework effectively handles common textual errors, including typos and inconsistent whitespace.
It also reliably identifies missing value placeholders, such as 'empty' and converts them to NaN, while only introducing minor miscorrections. 
For example, in the address\_1 column, baseline methods such as Cocoon and RetClean introduce unnecessary changes: Cocoon rewrites full addresses (e.g., '1720 university blvd' to '1720 university boulevard') and RetClean inconsistently changes capitalization. 
In contrast, the proposed framework explicitly follows the dominant dataset format and validates corrections, preventing such false positives.
Functional dependencies are effectively used to repair errors that cannot be corrected from the cell value alone. 
For instance, in the ProviderNumber column, the value 100x8 is correctly repaired using dependency and column-level context. 
Baselines like RetClean operate row-wise, resulting in inconsistent repairs (e.g., multiple formats for the same error in the State column: 'al' to 'Alabama', 'AL' or 'alabama') and preventing them from handling violations effectively. 
Similarly, Cocoon and Raha+Baran fail to detect and repair many functional dependency violations, likely because they do not identify the relevant column pairs as dependent.
Numeric columns with formatting inconsistencies, such as score (97\%) and sample (33 patients), are correctly converted to pure numeric types by removing extra non-numeric characters, improving downstream usability. 
While Cocoon also handles numeric standardization well, other baselines either ignore these inconsistencies or apply partial, inconsistent corrections, leaving columns with non-numeric characters that can cause issues in later analyses.
Across the dataset, the framework maintains high precision and recall, with few false positives or negatives. 
Rare errors occur when the LLM sets a detected error to NaN rather than inferring the correct value (e.g., in the PhoneNumber column). 
Some false negatives remain, especially for highly diverse errors where characters are randomly replaced. 
Both the framework (with sampled context) and Raha+Baran (with labeled examples) struggle to correct these cases because the errors are too irregular to define a generalized cleaning operation that can fix all instances.
\newline\newline
\textbf{Beers} - On the Beers dataset, the framework again demonstrates strong performance across numeric, categorical and relational attributes. 
Most errors are detected and corrected, resulting in high recall with minimal impactful false positives. 
This is mainly because the dataset contains columns with short, redundant strings or numeric values, both of which the LLM can handle effectively. 
For these columns, it is easier to generate generalized cleaning operations. 
In the brewery\_name column, the framework standardizes abbreviations such as 'Co.' to 'Company' when this is the dominant pattern, improving consistency. 
Only Raha+Baran applies a similar standardization, and only partially.
The city column is corrected both semantically and syntactically: misspellings are fixed, variants including state abbreviations are standardized to city names only and incorrect neighborhood entries like 'South Austin' are normalized to the correct city, 'Austin'. 
These corrections leverage contextual and semantic reasoning, which non-LLM methods cannot perform. 
Remarkably, Cocoon also does not fully apply these corrections. 
Minor false positives, primarily in cells containing string values, include converting curly apostrophes to straight ones or standardizing 'Saint' to 'St.' but these changes are low-impact.
Formatting inconsistencies in numeric columns ounces (12.0 oz, 12.0 ounce, 12.0 OZ.) and abv (0.09\%, 0.09, 0.046\%), are correctly converted to pure numeric types. 
This ensures consistency and usability for downstream analytical tasks. Baselines either perform conversions inconsistently or not at all, leaving noisy values. 
Outliers in the ibu column are correctly handled by the framework, which distinguishes between true outliers and outliers acting as placeholder values. 
True outliers are repaired by replacing them with the median value, while placeholders for missing data are converted to NaN. 
In contrast, all other baselines except SAGED fail to detect the outliers correctly.
Functional dependency reasoning further improves the framework's performance. 
For example, missing values in the state column are correctly imputed and errors in brewery\_id are repaired, both using dataset-level constraints derived from functional dependencies. 
In contrast, Cocoon and SAGED largely miss dependency violations, HoloClean applies constraints to impute missing values but fails to correct violations, and RetClean relies only on row-level context (e.g., using the city column to infer the state), resulting in incomplete repairs.
A notable example illustrating the effectiveness of using an LLM as a semantic decision-maker involves the dependency brewery\_name $\longrightarrow$ brewery\_id. 
Multiple rows corresponding to 'Oskar Blues Brewery'  have different IDs and cities because the brewery operates in multiple locations. 
This triggers a statistical dependency violation, and a naïve repair strategy based on majority voting would incorrectly overwrite these valid differences. 
In contrast, the LLM uses the row-level context to infer the true logic and preserves the legitimate variations, thereby maintaining semantic correctness rather than enforcing purely statistical consistency.
\newline\newline
\textbf{Movies} - On the Movies dataset, the proposed framework demonstrates strong performance across a wide range of structural, numeric and formatting error types. 
Overall, the framework achieves high recall and produces a consistent cleaned dataset, with most false positives limited to minor formatting changes rather than semantic errors.
The framework performs particularly well on pattern, format and duplication errors. 
In the id column, entries that deviate from the dominant identifier pattern are correctly detected and set to NaN, while all baseline methods fail to identify these violations. 
Similarly, duplicated values are consistently normalized, both in numeric fields such as year (e.g., '2005 2005') and in multi-value textual fields such as creator (e.g., 'Mark Brown,Mark Brown' to 'Mark Brown'). 
Placeholder descriptions (e.g., 'Add a plot', 'No description') are also correctly converted to NaN, resulting in cleaner and more consistent columns.
For the release\_date column, entries that deviate from the dominant format (e.g., 'Nov 11, 2011 USA' instead of '11 November 2011 (USA)') are standardized to a single consistent representation across the dataset. 
This contrasts with Cocoon, which converts dates into a different datetime format and thereby introduces many false positives, and with Raha+Baran and SAGED, which fail to detect these inconsistencies altogether.
As in the other datasets, the framework performs well on numeric columns. 
Format inconsistencies in the duration column, such as '55 min' and '1 hr. 23 min.', are correctly converted into a single numeric value. 
This highlights the advantage of LLM-based code generation, as it can handle mixed textual patterns that rule-based approaches struggle with. 
In contrast, Raha+Baran and Cocoon fail on mixed formats, for example converting '106 min.' to 106 while incorrectly converting '1 hr. 39 min.' to 1. 
Other numeric formatting issues are also handled effectively: values such as '6.7/10' in ratingValue are converted to pure numerics, and string-typed values in ratingCount (e.g., '379,998') are correctly parsed into integers. 
All entries are converted to either numeric values or NaN, resulting in columns that are directly usable for downstream machine learning tasks. 
While Cocoon applies similar conversions, Raha+Baran does so inconsistently, leaving a subset of values uncleaned. 
Outliers are also detected by the framework, whereas the baseline methods largely fail to identify them.
Most false positives in this dataset are minor and primarily related to formatting. 
The majority occur in the director column, where the framework inserts spaces after commas in name lists (e.g.,'Pierre Coffin,Chris Renau' to 'Pierre Coffin, Chris Renau'). 
While these changes are counted as false positives, they improve readability and could be corrected by a stricter validator. 
Cocoon applies similar formatting changes but does so across all multi-value columns. 
This demonstrates that LLMs may apply learned formatting habits even when explicitly instructed not to, as discussed earlier in the context of the importance of validation mechanisms.
\newline\newline
\textbf{Rayyan} - The Rayyan dataset poses significant challenges for automated data cleaning, resulting in a strong decline in performance for both the proposed framework and the baseline methods. 
The highly heterogeneous column formats, ambiguous fields and limited redundancy make it difficult for the LLM to infer consistent cleaning rules. 
Despite these challenges, the proposed framework achieves average cleaning performance and matches or exceeds the overall performance of the baseline methods.
For this analysis, we focus on column-level results, as they provide more meaningful insights here, while the other datasets show near-perfect scores across all columns. 
As shown in table \ref{tab:rayyan_metrics}, the framework performs best on more structured columns where format and pattern standardization can be applied. 
In the article\_language column, multiple representations (e.g., 'eng', 'ENG', 'English') are successfully normalized to a single consistent format, yielding high performance. 
In contrast, Raha+Baran overgeneralizes and incorrectly converts all entries to 'eng'. 
Similarly, in the journal\_issn column, the framework identifies the dominant ISSN pattern and attempts to repair deviations accordingly. 
When a valid repair cannot be inferred, values are correctly set to NaN, ensuring reliability for downstream use. 
This leads to strong performance, whereas Cocoon fails to detect most pattern violations and Raha+Baran overgeneralizes by repairing all violations to a single value. 
In the article\_pagination column, detection precision is high, but correction performance is lower. 
The column contains many distinct and irregular formats, making it difficult for the LLM to infer a dominant pattern. 
Detected errors are frequently replaced with NaN instead of being properly corrected, because the LLM cannot determine the correct value.
As a result, some errors remain uncorrected and others are only partially fixed. 
Similar to the other datasets, the framework effectively handles DMVs. 
In author\_list, placeholder values such as {NULL} are converted to NaN, while in article\_jvolume and article\_jissue, placeholder values such as -1 are correctly removed. 
Extreme outliers in these columns are detected and cleaned, although smaller outliers are missed. 
Notably, none of the baseline methods detect these outliers. 
Performance is weakest for free-text columns such as article\_title, journal\_title and author\_list, particularly in error correction. 
These columns contain a wide range of complex textual issues, including HTML entities, corrupt symbols and inconsistent formatting. 
While the framework successfully decodes some HTML-encoded strings (e.g., 'Does It \&quot;Work\&quot;?' to 'Does It "Work"?'), it struggles with corrupt symbols and cannot identify a consistent correction pattern. 
This limitation reflects the difficulty of reliably cleaning unstructured text, with baselines showing similar poor performance.

\subsection{Runtime and Token Usage}
The runtime results in table \ref{tab:runtimes} indicate that the proposed framework outperforms Raha+Baran and RetClean and achieves a runtime comparable to Cocoon. 
HoloClean is faster than the framework, but its cleaning performance is substantially lower. 
While Raha+Baran achieves similar cleaning quality to the proposed framework, it requires significantly more time, highlighting that the proposed framework is the more efficient choice for practical data cleaning.
\newline
Interestingly, the Movies dataset, which is the largest in terms of rows, has the shortest runtime. 
This is because the framework samples the dataset, making runtime largely independent of the number of rows. 
Instead, runtime scales with the number of columns and the number of detected functional dependencies. 
For example, the Hospital dataset has many columns and FDs, resulting in the longest runtime.
The Rayyan dataset also exhibits a relatively high runtime. 
As described earlier, difficulties in inferring consistent cleaning rules likely cause many operations to be rejected by the verifier, requiring multiple retries and increasing overall runtime.

\subsection{Ablation Study}
To evaluate the contribution of the different components of the proposed framework, we conducted an ablation study, comparing the full framework with three variants: one without the functional dependency detection tool, one without the validator and one using a basic prompt instead of a detailed, type-specific prompt. 
By analyzing changes in detection and correction performance across these variants, we can assess the relative importance of each component. 
For consistency, all results are averaged over two independent runs. The results are presented in figure \ref{fig:ablation_study}.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{Figures/combined_ablation_all.png}
    \caption{OLD! Barplot of ablation study results}
    \label{fig:ablation_study}
\end{figure}

When the dependency detection tool is removed, we focus on the Hospital and Beers datasets, as the other datasets do not contain functional dependencies. 
For the Hospital dataset, the impact is relatively small: F1 score for detection decreases from 0.99 to 0.96 and for correction from 0.96 to 0.91. 
Most FD violations in this dataset are simple typos, and the LLM can infer the correct values using column-level redundancy, minimizing the effect of removing the tool. 
On the Beers dataset, the performance drop is more noticeable, with F1 score for both detection and correction falling from 0.99 to 0.89. 
Missing values in the state column are no longer imputed and violations in the city column remain uncorrected, although most other cells are still cleaned correctly. 
From table \ref{tab:ablation_study}, we see that skipping the dependency detection tool slightly reduces runtime, as fewer LLM API calls are required, while token usage is largely unaffected. 
These results indicate that functional dependency reasoning is particularly valuable for repairing missing values and semantic violations that cannot be resolved using column-level context alone.
\newline\newline
Removing the validator has a more substantial effect on overall performance. 
For the structured and redundant Beers and Hospital datasets, the F1 score drops modestly, approximately five percentage points, because the LLM can still infer correct cleaning operations based on the consistent formatting in these datasets. 
Most formatting inconsistencies are repaired correctly and the few false positives are mostly due to minor deviations from the dominant format, such as changes in capitalization or abbreviation expansion, which the validator would normally prevent. 
For the Movies dataset, F1 score drops by 19 percentage points and for Rayyan, by 24 points. 
Movies has multiple valid cleaning options, while Rayyan is more heterogeneous and contains ambiguous entries. 
Without the validator, the LLM applies many incorrect changes, such as modifying date formats, altering the style of multi-value columns or changing capitalization, leading to a significant increase in false positives. 
Runtime and token usage are slightly reduced without the validator, since fewer retries are performed. 
This highlights the validator's critical role in maintaining precision, especially in datasets with complex or variable formatting.
\newline\newline
The variant using a basic prompt shows the largest performance decline. 
The prompts for both the recommender and validator are replaced with a basic prompt. 
This prompt contains only simple instructions for the LLM (e.g., to clean the data or enforce functional dependencies) and the same data sample from the original prompt, but excludes all type-specific instructions and examples.
In the Beers dataset, detection F1 score remains relatively high at 0.86, but correction F1 score drops sharply to 0.30. 
For Hospital, both detection and correction F1 score decrease by approximately 40 percentage points. 
The Movies dataset experiences a decline of around 50 points, and Rayyan drops by 28 points. 
The primary cause of this drop is that string values are often modified incorrectly: capitalization is changed inconsistently, abbreviations are expanded and metadata is removed, generating numerous false positives. 
Formatting corrections are also incomplete; for instance, numeric columns such as score, sample, ounces, and abv are not consistently standardized to pure numeric columns. 
Multi-value columns are frequently reformatted incorrectly (e.g., strings converted to lists or with added spaces after commas), further reducing precision. 
Despite these challenges, basic error types such as typos, DMVs, and pattern violations are still detected. 
Runtime is slightly longer for this variant due to additional retries needed for outputs to satisfy the validator, while token usage remains similar.
\newline\newline
Overall, the ablation study demonstrates that each component contributes meaningfully to the framework's performance, with prompt engineering having the largest impact. 
High-quality, type-specific prompts provide explicit instructions and examples, ensuring that the LLM applies cleaning operations consistently and according to the dataset's structure, rather than relying on generalized heuristics from its training data. 
Functional dependency reasoning and the validator further improve reliability by enabling context-aware corrections and preventing unwanted modifications, especially in complex or heterogeneous datasets.
